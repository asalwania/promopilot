# LLM calls take one tool step at a time, retry transient errors, fall back to the other live provider, and are costed per session in a context scope

E8 (#42) makes `promopilot.llm` robust enough for the agent graph. SPEC §9.6 asks for `complete_with_tools(tools, messages)`, an Anthropic provider, retries with exponential backoff, automatic fallback to the secondary provider, and per-session token and cost accounting with prices per model in config (ADR 0001). SPEC does not fix the tool-call types, how cassettes key tool requests, which errors are transient, the retry bounds, how the fallback is chosen, the prices, or how cost is attributed to a session. We chose these with the owner:

- **One step per call.** `complete_with_tools(tools: Sequence[ToolSpec], messages) -> ToolTurn` asks the model for its next step and returns it. `ToolSpec` (name, description, JSON-Schema input) and `ToolTurn` (text, tool calls with id, name and parsed arguments) belong to `promopilot.llm`, so the LLM layer does not depend on the agents' tool registry. The loop that runs tools and sends results back lives in the planner agent. `Message` gains a `tool` role (`tool_call_id` names the call it answers) and optional `tool_calls` on assistant turns; `ToolTurn.as_message()` builds that turn. We rejected a provider-driven loop with a handler callback: it would hide tool calls from the graph's trace and checkpointing.
- **Opaque provider state.** Anthropic requires the thinking blocks of an assistant turn to be sent back unchanged while its tool round is open. `ToolTurn.provider_state` and `Message.provider_state` carry them as opaque dicts; OpenAI ignores them. Mixing providers inside one tool round (fallback mid-round from OpenAI to Anthropic) may therefore be rejected by Anthropic. The planner restarts the round in that case (#47).
- **Cassettes.** A tool request hashes like a structured one (ADR 0019), with `tools` (the specs) in place of `schema`. Message fields at their defaults are left out of the hash, so every cassette recorded before tool calls existed keeps its hash. Tool-call ids stay in the hash: replay feeds recorded ids back, so a replayed round is consistent. `provider_state` is never hashed, keeping cassettes provider-independent. Each cassette also records the usage the call was billed for, outside the request, and replay reports it again. Old cassettes without usage replay with none.
- **Temperature and thinking.** OpenAI structured and tool steps run at temperature 0 (ADR 0022). `claude-sonnet-5` rejects sampling parameters with a 400, so Anthropic requests send none. The hash still records temperature 0, because it describes the request, not a provider. Anthropic runs with adaptive thinking at effort `low`, which keeps cost and latency down while leaving thinking on (disabling it can make models write tool calls as text).
- **Transient errors.** Timeouts, dropped connections, HTTP 408, 409 and 429, and any 5xx (including Anthropic's 529 overloaded) raise `TransientLLMError`, a subclass of `LLMError`. Everything else (400, 401, 403, 404, refusals, unparseable answers) is a plain `LLMError` and is not retried. SDK clients are built with `max_retries=0`, so retries happen in one place.
- **Retry bounds.** `RetryingProvider` makes at most 3 attempts, waiting 1 s then 2 s. The delay doubles and is capped at 8 s, and there is no jitter, so behaviour is deterministic and testable with a fake clock (an injected `sleep`). The worst case adds 3 s per provider.
- **Fallback.** `build_provider` wraps the live primary named by `LLM_PROVIDER` in `RetryingProvider`. If the other live provider's key and model are set, it becomes the retried secondary behind `FallbackProvider`. Otherwise a `llm_no_fallback` warning is logged. The secondary takes over after the primary gives up for any `LLMError`, including a permanent one such as a bad key; if both fail, the error names both. Replay never falls back: a cassette miss must fail loudly.
- **Prices.** `LLM_PRICES` is a JSON map from model id to `input_usd_per_mtok` and `output_usd_per_mtok`, and `USD_INR_RATE` converts to rupees, because SPEC §6 sets the target of under ₹20 per session. Prices are keyed by the configured model id, never the dated snapshot a provider echoes back. A model with no price still counts its tokens; its cost is left out and it is listed in `unpriced_models`. Defaults, checked on 2026-09-26:
  - `gpt-4.1-mini`: $0.40 in, $1.60 out per million tokens, standard tier ([OpenAI pricing](https://developers.openai.com/api/docs/pricing)).
  - `claude-sonnet-5`: $2 in, $10 out per million tokens ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing); the $2/$10 launch price became the standard price).
  - `USD_INR_RATE=96`: USD/INR was 95.9 on 2026-09-25 ([Trading Economics](https://tradingeconomics.com/india/currency)).

  Cache pricing is not modelled: we send no cache breakpoints.
- **Per-session cost.** One provider instance serves every concurrent session, so usage cannot live on the provider. Each live provider reports every billed call (including refusals) with `record_usage`. A session opens `with track_usage() as meter:`, a scope held in a context variable, so each asyncio task counts only its own calls. Scopes nest: `RecordingProvider` opens one per call to write that call's usage into the cassette. `meter.totals(prices, usd_inr_rate=...)` gives calls, tokens and cost in dollars and rupees. Emitting token-usage trace events and storing session totals is #45.

## Consequences

- `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `LLM_PRICES` and `USD_INR_RATE` are new settings (`.env.example`). The price table must be updated by hand when list prices change.
- Live checks in `tests/live` are marked `live` and excluded by default. They are run deliberately, with keys exported, and never in CI.
- This supersedes ADR 0019's "`anthropic` fails with a pointer to E8" and extends its cassette format with `usage`.
